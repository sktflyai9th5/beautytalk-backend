# 립 화장 확인 어시스턴트 — 백엔드 인계 패키지

시각장애인 사용자의 셀피를 받아 립 상태를 음성 안내용 한국어로 돌려준다.
**파인튜닝 없음.** 시스템 프롬프트 + few-shot 예시 3장으로만 동작한다.

## 파일

| 파일 | 용도 |
|---|---|
| `system_prompt.txt` | 시스템 프롬프트. 매 요청에 그대로 넣는다 |
| `fewshot/fewshot.json` | 예시 3턴 (이미지·질문·답변). **순서 유지** |
| `fewshot/0*.{jpg,png}` | 예시 이미지 |
| `preprocess.py` | EXIF 보정 + 립 크롭. **모델 호출 전 필수** |
| `inference.py` | 요청 조립 참조 구현 (`build_messages`) |
| `config.json` | 모델·이미지·생성 파라미터 **기록용** (§10 참고) |
| `face_landmarker.task` | MediaPipe 모델 (preprocess 가 사용) |

## 흐름

```
셀피 → preprocess.prepare()  ─ 실패 → PrepError.message 를 그대로 TTS
                             └ 성공 → build_messages() → 모델 → 응답을 그대로 TTS
```

# 백엔드 연동

## 해야 할 일 체크리스트

- [ ] 의존성 고정 설치 (§1. **transformers 가 5.x** 라는 점 주의)
- [ ] `pillow-heif` 등록 — 아이폰 기본이 HEIC 라 없으면 iOS 업로드가 전부 예외 (§6)
- [ ] 부팅 시 모델 적재 + 전처리기 워밍업 → 그 다음에 헬스체크 통과 (§2, §3)
- [ ] 전처리를 GPU 큐 **앞**에 배치 (§4)
- [ ] `prepare()` 를 try 로 감쌀 것 — PrepError 로 안 잡히는 예외가 있다 (§5)
- [ ] MediaPipe 검출기를 스레드마다 하나씩 — 지금 코드는 락 없는 전역 공유다 (§3)
- [ ] 앱과 입력 계약 합의 — 포맷 / 최소 해상도 / **미러링 플래그** (§6)
- [ ] 응답 새니타이저 + 실패 폴백 문구 (§7)
- [ ] 첫 측정용 로깅 (§8)
- [ ] 이미지 보존 정책 결정 (§9)

## 1. 환경

검증에 쓴 버전이다. **transformers 가 5.x** 이므로 4.x 기준 예제 코드는 맞지 않는다.

```
python==3.11.9
torch==2.11.0+cu128
transformers==5.5.0
mediapipe==1.0.0
unsloth==2026.8.18
bitsandbytes==0.50.1
accelerate==1.14.0
pillow==12.3.0
numpy==2.4.6
pillow-heif          # iOS HEIC 업로드용. 검증 환경엔 없었으나 실사용에 필요
```

## 2. 모델 적재 (부팅 시 1회)

아래 성능 수치는 **unsloth 로더 기준**으로 측정됐다. 순정 transformers 로 올려도
돌아가지만 같은 수치를 보장하지 않는다.

```python
from unsloth import FastVisionModel

model, processor = FastVisionModel.from_pretrained(
    "unsloth/Qwen3-VL-8B-Instruct-unsloth-bnb-4bit",
    load_in_4bit=True, dtype=None,
    use_gradient_checkpointing="unsloth")
processor.tokenizer.model_max_length = 16384   # few-shot 3턴이 들어가므로 필요
FastVisionModel.for_inference(model)
```

VRAM 7.7GB. 부족하면 `Qwen3-VL-4B-Instruct` 로 내려도 few-shot 시 동급이었다.

## 3. 전처리기 준비 (부팅 시 1회)

`preprocess.py` 의 `_detector` 는 지금 **락 없는 전역 싱글턴**이다. MediaPipe
FaceLandmarker(IMAGE 모드)는 스레드 안전이 보장되지 않으므로 멀티스레드 워커에
그대로 붙이면 안 된다. 스레드마다 하나씩 만들거나 락으로 직렬화할 것.

검출기 최초 생성에 **468ms** 가 든다. 헬스체크 통과 전에 워밍업해서 첫 사용자가
이 비용을 내지 않게 한다.

```python
import threading
from concurrent.futures import ThreadPoolExecutor

_local = threading.local()
POOL = ThreadPoolExecutor(max_workers=3)     # 스레드당 검출기 1개

def warmup():
    list(POOL.map(lambda _: prepare(SAMPLE), range(6)))   # 스레드 수의 2배는 태워야 다 채워짐
```

`prepare()` 자체는 중앙값 **13ms** (CPU, 최소 10 / 최대 26). 스레드 3개면 GPU 가 먼저 막힌다.

## 4. 요청 처리 흐름

```
업로드
  → prepare()   13ms, CPU
      ├ 실패 → PrepError.message 를 그대로 TTS. 여기서 끝 (GPU 안 씀)
      └ 성공 ↓
  → GPU 큐 적재
  → build_messages() → model.generate()
  → 새니타이즈 → TTS
```

**전처리를 GPU 큐 앞에 두는 것이 중요하다.** 거부 사유가 GPU 를 기다리지 않고 즉시
나간다. 앞이 안 보이는 사용자는 프레이밍 실패로 재촬영을 여러 번 반복하는 것이 정상
사용 패턴이라, 이 왕복 지연이 체감 품질을 좌우한다. 전처리를 GPU 워커 안에 넣으면
실패할 요청이 GPU 슬롯을 잡아먹는다.

## 5. `prepare()` 계약

성공하면 `(PIL.Image, None)`, 실패하면 `(None, PrepError)`.
`PrepError.message` 는 **그대로 TTS 로 내보낼 수 있는 한국어 문장**이다. 가공하지 말 것.

| `code` | 조건 | `message` |
|---|---|---|
| `too_dark` | 원본 평균 밝기 40 미만 | 사진이 너무 어두워요. 밝은 곳에서 다시 찍어 주세요. |
| `no_face` | 얼굴 미검출 | 얼굴이 잘 안 보여요. 휴대폰을 얼굴에서 한 뼘 정도 떨어뜨리고 정면으로 들어 주세요. |
| `lip_too_small` | 입술 폭 60px 미만 | 입술이 너무 작게 나왔어요. 휴대폰을 얼굴 쪽으로 조금 더 가까이 가져와 주세요. |

**주의: 모든 실패가 PrepError 로 오지 않는다.** `Image.open()` 이 던지는 예외
(`FileNotFoundError`, `UnidentifiedImageError`, 잘린 업로드의 `OSError`, HEIC 미지원)는
감싸이지 않고 그대로 올라온다. 반드시 try 로 감싸고 예외용 폴백 문구를 둘 것.

```python
try:
    img, err = prepare(upload)          # 경로 / PIL.Image / BytesIO 모두 받는다
except Exception:
    log.exception("prepare")
    return "사진을 읽지 못했어요. 다시 한 번 찍어 주세요."
if err:
    return err.message                  # 그대로 TTS
```

HTTP 업로드는 `BytesIO` 로 그대로 넘기면 된다.

## 6. 앱과 합의해야 할 입력 계약

**포맷.** 아이폰 기본은 HEIC 다. `pillow_heif.register_heif_opener()` 를 호출하거나,
앱이 JPEG 로 변환해 올리도록 못박을 것. 안 하면 iOS 업로드가 통째로 예외가 난다.

**최소 해상도.** `MIN_LIP_W = 60` 은 *업로드된 이미지의 픽셀* 기준이라 업로드 해상도에
따라 의미가 조용히 바뀐다. 검증 사진들의 입술 폭은 임계값의 2.5~9.0배로 여유가 있지만
그건 잘 잡힌 사진 기준이다. 사용자가 팔을 뻗어 얼굴이 프레임의 절반만 차지하면 반토막
난다. **긴 변 1080px 이상**을 계약에 넣기를 권장한다. 앱이 더 줄여서 올려야 한다면
임계값을 이미지 크기 비율로 바꿔야 하는데, 그건 재측정 대상이다.

**미러링 — 결정해야 할 사항이다.** `ImageOps.exif_transpose` 는 EXIF 에 기록된
반전(orientation 2·4·5·7)만 되돌린다. 전면 카메라 미러링은 보통 orientation=1 로
픽셀에 이미 구워져 저장되므로 잡히지 않는다. **지금 파이프라인에 미러 복원은 없다.**
앱이 프리뷰 그대로 저장하면 좌우 안내가 계통적으로 뒤집히고, 이것은 사용자가 스스로
확인할 수 없는 종류의 오류다. 추론하지 말고 업로드 요청에 `mirrored: bool` 을 두고
`prepare()` 앞에서 되돌릴 것.

**질문 문구 (`user_text`).** `build_messages(img, user_text)` 의 기본값은 `"립 봐주라."` 다.
few-shot 예시 질문 3개가 서로 다른 표현인 것은 STT 변주를 견디게 하려는 설계이므로,
사용자 발화를 STT 로 받아 그대로 넘기면 된다. 빈 문자열이면 기본값을 쓸 것.

## 7. 출력 처리

모델 응답은 **원문 그대로 TTS 로 읽어 준다.** 요약·재작성·말투 변경 금지.
`inference.action_of()` 는 로깅·지표 전용이며, 사용자에게 나가는 문구를 만드는 데
쓰지 않는다.

형식 위반 0건이라는 검증 결과는 n=32 기준이다. 값싼 후처리 하나를 두기를 권장한다.
마크다운 기호나 괄호가 섞여 들어오면 TTS 가 그대로 읽는다.

```python
FALLBACK = "지금은 확인이 어려워요. 잠시 뒤에 다시 찍어 주세요."

def sanitize(t):
    t = re.sub(r"[*_#`\[\](){}<>]", "", t or "").strip()
    return t if t else FALLBACK
```

생성 실패·타임아웃·빈 응답에도 같은 폴백 문장을 쓴다. 조용히 끊기면 사용자는 아무
정보도 받지 못한다.

## 8. 첫 측정을 위한 로깅

`인계 시 반드시 알아야 할 것` 4번(신선한 사진 재측정)에 필요한 데이터를 이 단계에서 모은다.

- **`PrepError.code` 별 분포** — 어떤 재촬영 안내가 실제로 많이 나가는지.
  특히 `too_dark` 는 크롭 전 원본 전체 평균 밝기로 판정하므로 어두운 배경·피부톤에서
  과반려할 수 있다. 반려가 특정 조건에 쏠리는지 확인할 것
- **입술 bbox 폭 분포** — `MIN_LIP_W` 조정 판단의 유일한 근거
- **`action_of()` 결과 분포** — ok / wipe / blend 비율이 검증 때와 크게 다르면 신호
- **요청당 지연** — 전처리와 GPU 를 나눠서

## 9. 이미지 보존 정책 — 백엔드가 결정해야 함

사용자 얼굴 셀피다. 재측정하려면 크롭을 남겨야 하고, 남기려면 동의가 필요하다.
정하지 않은 채로 두면 기본값으로 계속 쌓인다. 배포 전에 결정할 것.

## 10. 손대면 안 되는 것

- `system_prompt.txt`, `fewshot/` 3장과 그 **순서**
- `PAD_X=0.50`, `PAD_Y=0.70`, 랜드마크 인덱스 `OUTER`,
  처리 순서(EXIF → 검출 → 크롭 → 리사이즈)
- `config.json` 은 **기록용이다.** `preprocess.py` 는 이 파일을 읽지 않는다.
  `pad_x` / `query_max_side` 를 여기서 고쳐도 아무 일도 일어나지 않는다.
  실제 값은 `preprocess.py` 상단 상수이므로, 바꿀 일이 있으면 **양쪽을 같이** 고칠 것

---

## 출력 규약

세 가지 동작 중 하나로 안내한다. 사용자에겐 **모델 응답 원문을 그대로** 읽어 주고,
`action_of()` 는 로깅·지표용으로만 쓴다.

- `ok` — 고칠 곳 없음. 확인한 근거를 들어 안심시킴
- `wipe` — 번짐. 부위 + "입술선 바깥 방향으로 닦아내기"
- `blend` — 덜 펴발림. 부위 + "덧발라 고르게 펴 바르기"

응답은 2~3문장 60~90자. 마크다운·기호·이모지·괄호·좌표는 나오지 않는다(검증 32/32 위반 0건).

## 성능 (dev 32장, 2026-08-21)

| 지표 | 맨몸 | 시스템만 | **+few-shot** |
|---|---|---|---|
| 동작 일치 | 41% | 50% | **72%** |
| 결점 유무 | 41% | 53% | **84%** |
| 번짐 | 0/8 | 3/8 | **8/8** |
| 덜펴발림 | 0/11 | 0/11 | 4/11 |
| 헛짚음 | 0/13 | 0/13 | 2/13 |
| 응답 길이 | 306자 | 140자 | **62자** |

> **이 표는 현재 프롬프트가 아니라 sys4 원문 기준이다.** 당시 넷째 원칙은 *오탐 우선*
> ("문제 없는데 지적하는 것은 놓치는 것보다 나쁘다")이었고, 지금 파일에는 그 조항이
> **미탐 우선으로 반전되어** 들어가 있다(아래 5번). 따라서 **헛짚음 2/13 과 결점 유무
> 84% 는 재측정 대상**이다. 나머지 행은 영향이 적다.

> **맨몸 열의 헛짚음 0/13 은 좋은 수치가 아니다.** 아무 결점도 못 찾아서(번짐 0/8,
> 덜펴발림 0/11) 헛짚을 일이 없었던 것이다. 헛짚음은 낮을수록 좋은 지표라 오독하기 쉽다.

## 인계 시 반드시 알아야 할 것

1. **전처리를 건너뛰지 말 것.** 얼굴 전체 사진을 그대로 넣으면 성능이 검증치와 달라진다.
   크롭 패딩(0.50 / 0.70)도 검증에 쓴 값이라 바꾸면 재측정이 필요하다.
2. **예시 3장은 세트다.** 교체·추가·순서 변경 시 성능이 크게 흔들린다
   (예시 1장 교체로 정상 판별이 10/14 → 7/14 로 무너진 사례 있음).
3. **덜펴발림 4/11 은 알려진 한계.** 번짐과의 경계 사례에서 갈린다. 프롬프트로는
   여기가 상한이고, 개선은 파인튜닝 영역.
4. **dev 32장에 반복 튜닝한 수치다.** 신선한 사진 20~30장 측정이 아직 안 됐으므로
   72% 는 상한으로 보는 것이 안전하다.
5. **미탐 우선 정책 — 아직 검증 전이다.** 확실하지 않으면 놓치기보다 짚어 주도록
   프롬프트에 명시돼 있다(번진 립은 착색되어 되돌리기 어렵기 때문). 이것은 단순 추가가
   아니라 **기존 조항의 방향을 뒤집은 것**이고, 성능 측정 이후에 들어갔다.
   첫 측정 때 오탐이 늘었는지 반드시 확인할 것.
6. **실사용 경로로 측정된 것은 32장 중 7장뿐이다.** dev set 은 25장이 이미 입술
   클로즈업(`crop=asis`)이고, 전체샷 → MediaPipe 크롭을 실제로 거친 것은 7장이다.
   그 7장에는 **덜펴발림 케이스가 0장**이다(ok 4, wipe 3). 즉 3번의 "덜펴발림 4/11"은
   전부 입술샷에서 나온 숫자이고, 실사용 파이프라인에서 덜펴발림이 어떻게 나오는지는
   아직 한 장도 관측되지 않았다. 실사용자는 스스로 프레이밍할 수 없으므로 전체샷이
   기본 입력이 된다.
7. 모델은 8B-4bit(VRAM 7.7GB) 기준. 4B 로 내려도 few-shot 시 동급이었다.

## 다음 단계 (미완)

- 신선한 사진 20~30장으로 1회 측정 → 과적합분 확인. **덜펴발림 케이스를 전체샷으로**
  확보하는 것이 최우선 (위 6번)
- 미탐 우선 반전 이후 헛짚음·결점 유무 재측정
